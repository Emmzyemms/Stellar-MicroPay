# Adding a New Locale

Stellar MicroPay's frontend ships with a tiny, dependency-free i18n layer: JSON
catalogs in [`frontend/locales/`](../frontend/locales/), loaded and resolved by
[`frontend/lib/i18n.ts`](../frontend/lib/i18n.ts). Adding a language means
copying the English catalog, translating its **values**, and registering the
locale in one TypeScript file. The settings language picker and the document
`lang`/`dir` attributes pick it up from there.

Currently shipped: **English (`en`)**, **Spanish (`es`)** and **Arabic (`ar`)**.
This guide is written for a new locale such as French (`fr`); substitute your
language's code throughout.

> **Scope:** This guide documents the current system. The catalog and code
> snippets below are real files, not pseudocode. If the implementation changes,
> update this page in the same pull request.

## How the pieces fit together

| File | What it does |
| --- | --- |
| `frontend/locales/en.json` | Source of truth for keys. Every other catalog mirrors it. |
| `frontend/locales/es.json`, `frontend/locales/ar.json` | Shipped translations. Keep them at 100% key parity with `en.json`. |
| `frontend/lib/i18n.ts` | Imports the catalogs, declares `Locale`, `SUPPORTED_LOCALES`, `LOCALE_LABELS`, `MESSAGES`, the RTL list and `isLocale()`, and selects plural forms with `Intl.PluralRules`. **This is the only source file you must register a locale in.** |
| `frontend/contexts/I18nContext.tsx` | Provides `t()`, the active locale, `setLocale()`, `resetLocale()` and `availableLocales` to React components. Persists the choice to `localStorage` and resolves the first-visit locale. |
| `frontend/pages/settings.tsx` | Renders the language picker from `SUPPORTED_LOCALES` and `LOCALE_LABELS`. No edit is needed when you add a locale. |
| `frontend/__tests__/i18n.test.tsx` | Core translate/fallback/RTL tests, catalog key-parity and empty-string checks, and provider tests. |
| `frontend/__tests__/i18n-fallback.test.ts` | Proves missing keys fall back to English (see below). |
| `frontend/__tests__/i18n-screens.test.tsx`, `frontend/__tests__/i18n-send-form.test.tsx` | Render real screens in English and Spanish. |

Components use the `useTranslation()` hook:

```tsx
import { useTranslation } from "@/contexts/I18nContext";

const { t } = useTranslation();
<h1>{t("settings.language.title")}</h1>;
```

Language changes apply immediately, are remembered in
`localStorage` under `stellar-micropay:locale`, and update
`<html lang>` / `<html dir>` through `applyDocumentLocale()`.

## Locale resolution and detection

On a first visit the app does not assume English: the initial locale is
resolved in `frontend/lib/i18n.ts` when `I18nProvider` mounts, in this order
(`resolveInitialLocale()`):

1. **An explicit choice** — the value the visitor picked in Settings, stored
   under `stellar-micropay:locale`. It always wins, so detection can never
   override a manual selection.
2. **The browser's preferred languages** — `navigator.languages` (most preferred
   first), then `navigator.language`, matched against the shipped catalogs by
   primary subtag. `es-MX`, `es-ES` and `es-419` all open `es.json`; `en-GB`
   opens English; `ar-EG` opens Arabic.
3. **English** — unsupported languages (`fr-FR`, `de-DE`, …) and SSR (no
   `navigator`) fall back to `en.json`. `he` is a valid `Locale` for RTL layout
   (#1318) but ships no catalog, so a Hebrew browser is unsupported and gets
   English text.

Detection only *reads* the browser: it never writes to `localStorage`, so the
locale keeps following the browser until the visitor chooses one. Choosing a
language in **Settings → Language** calls `setLocale()`, which persists the
override; the **Use browser language** button next to the picker calls
`resetLocale()`, which clears the override and re-runs detection.

Every `localStorage` call is wrapped in `try`/`catch`, so a private-mode
`SecurityError` degrades to detection (and ultimately to English) instead of
breaking the page. `I18nProvider` starts from English because hydration cannot
read `navigator` or storage; the resolved locale is applied in a mount effect.

The detection matrix and the override precedence are covered by
`frontend/__tests__/i18n.test.tsx` → `browser locale detection (#1459)`.

## Step-by-step: add a locale

### 1. Create a branch

```bash
git checkout -b docs/adding-a-locale   # for this guide
# or, for a translation:
git checkout -b feat/add-french-locale
```

### 2. Copy the English catalog

```bash
cp frontend/locales/en.json frontend/locales/fr.json
```

Use the lowercase [BCP 47](https://www.rfc-editor.org/info/bcp47) primary
language subtag as the file name (`fr`, `de`, `pt`, `ja`, …). If a locale needs
a region or script subtag, use the form the codebase agrees on (for example
`pt-BR`) and use the exact same string in every registration point below.

### 3. Translate the values — never the keys

Open `frontend/locales/fr.json` and replace every English **value** with your
translation. Leave all object keys, nesting and `{placeholders}` unchanged.

```json
{
  "settings": {
    "language": {
      "title": "Langue",
      "label": "Langue d'affichage",
      "hint": "Les modifications s'appliquent immédiatement et sont mémorisées dans ce navigateur."
    }
  },
  "dashboard": {
    "selectedPeriod": "Période sélectionnée : {label}",
    "outgoingPayments": {
      "one": "{count} paiement envoyé",
      "other": "{count} paiements envoyés"
    }
  }
}
```

Do not add, rename or reorder keys relative to `en.json`; keeping the same order
makes reviews and future diffs much easier. Do not leave empty strings — the
test suite rejects them.

### 4. Register the locale in `frontend/lib/i18n.ts`

There is no locale auto-discovery, so a catalog file alone is not loaded.
Make all seven edits below (the comments are only for this guide):

```ts
// 1. Import the catalog next to the existing ones.
import en from "@/locales/en.json";
import es from "@/locales/es.json";
import ar from "@/locales/ar.json";
import fr from "@/locales/fr.json";

// 2. Add the code to the Locale union. Keep "he": it is reserved for a future
//    Hebrew catalog and currently serves the English strings.
export type Locale = "en" | "es" | "ar" | "he" | "fr";

// 3. Add it to the picker order. English first, then alphabetically by label
//    or by code — match the order the project uses.
export const SUPPORTED_LOCALES: readonly Locale[] = ["en", "es", "ar", "fr"];

// 4. If (and only if) the language is right-to-left, add it here. RTL locales
//    automatically get dir="rtl" via applyDocumentLocale().
export const RTL_LOCALES: readonly Locale[] = ["ar", "he"];

// 5. Use the language's own name, not the English exonym and not a flag.
export const LOCALE_LABELS: Record<Locale, string> = {
  en: "English",
  es: "Español",
  ar: "العربية",
  he: "עברית",
  fr: "Français",
};

// 6. Wire the imported catalog into the lookup table.
const MESSAGES: Record<Locale, MessageTree> = {
  en: en as MessageTree,
  es: es as MessageTree,
  ar: ar as MessageTree,
  he: en as MessageTree, // Hebrew falls back to English strings with RTL direction
  fr: fr as MessageTree,
};

// 7. Extend isLocale()'s allow-list. It is hand-written, not derived from
//    SUPPORTED_LOCALES, so a missed entry makes stored values fall back to en.
export function isLocale(value: unknown): value is Locale {
  return (
    typeof value === "string" &&
    (["en", "es", "ar", "he", "fr"] as readonly string[]).includes(value)
  );
}
```

If you add an RTL language (Hebrew, Persian, Urdu, …), add it to
`RTL_LOCALES` as well. `applyDocumentLocale()` will set `dir="rtl"` and the app
already includes RTL layout support; the tests cover `ar` and `he` today.

### 5. The settings picker needs no edit

`frontend/pages/settings.tsx` maps over `SUPPORTED_LOCALES` and reads
`LOCALE_LABELS[supportedLocale]`. Once step 4 is complete, your language
appears in **Settings → Language** automatically. If it does not, check that
the locale was added to *both* `SUPPORTED_LOCALES` and `LOCALE_LABELS`.

### 6. Update the tests that enumerate locales

The tests intentionally hard-code expectations so adding a language is a
reviewable change. In `frontend/__tests__/i18n.test.tsx`:

- Add the new catalog to the parity and empty-string assertions in
  `describe("locale files")`:

  ```ts
  expect(collectKeys(fr).sort()).toEqual(collectKeys(en).sort());
  // and include `fr` in the [en, es, ar] empty-string scan
  ```

- Update `SUPPORTED_LOCALES` / `isLocale()` expectations if they list locales.
- Update the provider probe's expected `availableLocales` string
  (`"en,es,ar"` currently) and the locale buttons if you extend them.
- Add a small assertion for at least one translated value, e.g.
  `expect(translate("fr", "common.cancel")).toBe("Annuler");`, so a completely
  broken import cannot slip through.

If you add RTL support, update the `isRTL()` / `RTL_LOCALES` expectations too.
See [Running the i18n tests](#running-the-i18n-tests) for the commands.

### 7. Review the result in the browser

```bash
cd frontend
npm run dev
```

Open **Settings**, switch to the new language, then confirm:

- the picker label is in the language's own script;
- navigation, dashboard and send-payment screens show translated copy;
- the choice survives a page reload (`localStorage`);
- `<html lang="fr">` is set, and `<html dir="rtl">` for RTL languages.

### 8. Commit and open a pull request

Keep the catalog, `frontend/lib/i18n.ts` and the test updates in one focused
PR. Use the project's Conventional Commits style, for example:

```bash
git commit -m "feat(i18n): add French locale"
```

Link the relevant locale-request issue in the PR body (`Closes #…`) and mention
whether a native speaker has reviewed the translation.

## Key structure and naming

Catalogs are **nested objects of strings** addressed with dot paths:

```json
{
  "common": { "cancel": "Cancel" },
  "settings": {
    "language": { "title": "Language" },
    "network": { "switchToMainnet": "Switch to Mainnet" }
  }
}
```

- **Namespaces** group keys by feature/screen: `common`, `navbar`, `settings`,
  `dashboard`, `sendPayment`, `pwaUpdate`. A screen-specific key belongs in that
  namespace, not in `common`.
- **Key names** are `lowerCamelCase` and describe the UI slot, not the English
  sentence: `settings.language.hint`, not `settings.language.changesApply...`.
  This lets translators reword without keys going stale.
- **Depth** stays shallow (normally two or three levels). Resolve keys with the
  full dot path, e.g. `t("settings.network.customHorizonHint")`.
- **Values are strings** — with one exception: a plural group is a nested
  object of plural-category strings (see
  [Plurals and counts](#plurals-and-counts)). No arrays, numbers or booleans. Do
  not embed HTML or JSX; the renderer inserts the string as text.
- **Placeholders** use `{name}` with `lowerCamelCase` names: `{count}`,
  `{label}`, `{asset}`, `{amount}`, `{username}`, `{used}`, `{max}`. Translate
  the sentence around them but keep every token byte-for-byte identical.
  `{{name}}` is also accepted, but every shipped catalog uses single braces, so
  match the surrounding file. Unknown/missing values are left as `{name}` rather
  than rendering `undefined`; that is a safety net, not a reason to drop a
  token.
- **Punctuation and spacing** around a placeholder belong to the translation.
  For example, French inserts a space before `:` and may move the token.
- **Do not concatenate translated fragments** in components. Add a whole
  sentence with placeholders instead, so word order can differ by language.

## Plurals and counts

`translate()` selects the plural form with `Intl.PluralRules`, so the caller
passes a **count** and never writes a `count === 1 ?` ternary. A key that varies
by count is stored as a **nested object** whose children are CLDR plural
categories instead of a string:

```json
"dashboard": {
  "outgoingPayments": {
    "one": "{count} outgoing payment",
    "other": "{count} outgoing payments"
  },
  "incomingPayments": {
    "one": "{count} incoming payment",
    "other": "{count} incoming payments"
  }
}
```

```tsx
t("dashboard.outgoingPayments", { count }); // "1 outgoing payment" / "4 outgoing payments"
```

### The convention

- **Shape:** a plural group is an object at the normal dot path (`contacts.count`)
  with one child per plural category. `{count}` is the placeholder the sentence
  interpolates; other placeholders (`{shown}`, `{asset}`) may appear alongside it.
- **`other` is required**, and is the fallback for any category the file does not
  define. `zero`, `one`, `two`, `few` and `many` are optional.
- **`one`/`other` is the minimum** for a new key. Add `few`/`many`/… only when
  the target language needs them and you are confident in the forms — for
  example Arabic selects `zero`/`one`/`two`/`few`/`many`/`other` and currently
  defines only `one`/`other`, so `3` renders the `other` string.
- **Never a suffix convention.** Do not add `…Plural` / `…Plural2` keys; the
  engine derives the category from the locale, which is the point of using
  `Intl.PluralRules`.
- **Selection is on the number in `count`.** The active locale's rule wins; a
  missing category (or a missing key) falls back the same way strings do —
  active locale `other` → English category → English `other`.
- **A key with no `count`** is looked up as a plain string, so a countless call
  returns `other`'s sibling only when the key is a plain string.

### Rules for translators

- Define `other` always; define `one` whenever your language has a distinct
  singular (English and Spanish both do).
- Follow the target language's CLDR rules, not English's. English uses the
  plural form for `0` (`0 outgoing payments`); a language with a real `zero`
  category should add a `zero` key rather than overloading `one`.
- Translate the noun correctly for the number and keep `{count}`; a plural group
  is always counted, so dropping the token loses information.
- Keep the nesting order stable (`zero`, `one`, `two`, `few`, `many`, `other`)
  so diffs stay readable, and keep the group in the same position in every
  catalog.
- For counts rendered outside the catalogs, the shared helper
  [`pluralize()`](../frontend/utils/intlFormatters.ts) in `intlFormatters.ts`
  exposes the same `Intl.PluralRules` behavior for non-JSON strings; see
  [`docs/intl-formatting.md`](./intl-formatting.md).

### Composing optional clauses

A sentence with two independent counts (for example an import toast that reports
imported and skipped rows) cannot be expressed by one category. Use one plural
group per clause and join the finished clauses with neutral punctuation — never
concatenate a stem and an ending:

```tsx
const imported = t("contacts.imported", { count: fresh.length });
const skipped = t("contacts.duplicatesSkipped", { count: duplicates });
showToast(duplicates > 0 ? `${imported} · ${skipped}` : imported);
```

## Translation quality guidelines

**Do not translate product, protocol and network names.** Keep these exactly as
written in English (Latin script where the product uses it):

- **XLM**, **USDC**, **AQUA** and other asset tickers
- **Stellar**, **Soroban**, **Horizon**, **Freighter**, **Friendbot**
- **SEP-0007**, **SEP-0010**, contract/function names and code identifiers
- **Testnet** / **Mainnet**: these are network names. The Spanish catalog keeps
  them as-is; the Arabic catalog transliterates them and adds the English name
  in parentheses, e.g. `شبكة الاختبار (Testnet)`. Pick the convention that reads
  naturally in your language and is consistent across the file.

Also:

- **Never translate keys, placeholder names, file names or `{count}`.**
- **Write for the UI, not word-for-word.** Keep strings short enough for buttons
  and labels; match the tone of existing copy (the Spanish catalog uses an
  informal "tú" address consistently).
- **Use native names in `LOCALE_LABELS`** (`Français`, `Deutsch`, `日本語`), not
  English names or flag emoji. A language is not a country.
- **Use the target language's punctuation**, quotation marks and ellipsis
  conventions. Preserve meaningful symbols such as `→` or `…` when they are
  part of the layout, or replace them with the local equivalent.
- **Be consistent.** Pick one term per concept (e.g. "wallet" → "cartera" in
  Spanish) and use it everywhere. Check [`GLOSSARY.md`](../GLOSSARY.md) for the
  project's terminology.
- **Prefer human review.** Machine translation is a starting point only. Ask a
  native or fluent speaker to review, especially for financial warnings such as
  the Mainnet switch confirmation, where a mistranslation can cause real loss.
- **Do not pad.** Empty strings, copied English values and placeholder-only
  "translations" are treated as incomplete; the test suite rejects empty values.

## Fallback and key parity

`translate(locale, key)` resolves in this order:

1. the active locale's catalog;
2. **English** (`en.json`);
3. the raw key string itself.

So a missing key never renders `undefined` — it renders English, then the key.
This is a safety net for development, **not** an acceptable shipped state: a
new locale must define every key that `en.json` defines. Do not rely on
fallback to hide untranslated strings.

The contract is enforced by
[`frontend/__tests__/i18n-fallback.test.ts`](../frontend/__tests__/i18n-fallback.test.ts)
and the `describe("locale files")` block in
[`frontend/__tests__/i18n.test.tsx`](../frontend/__tests__/i18n.test.tsx):

- active-locale strings win;
- missing active-locale keys fall back to English;
- unknown keys fall back to the key;
- the shipped catalogs (`es`, `ar`) have exactly the same flattened key set as
  `en.json`;
- no shipped catalog contains an empty string.

These assertions are per-catalog, not auto-discovered, so add your new catalog
to the lists when you add it (step 6 above). That is what makes your locale's
parity a test failure rather than a review-only promise.

## Running the i18n tests

Run from the `frontend/` directory. Install dependencies once if you have not
already:

```bash
cd frontend
npm install
```

Then run the four i18n suites together:

```bash
npm test -- i18n
```

This expands to `jest --runInBand i18n` and runs:

- `__tests__/i18n.test.tsx` — core translation, interpolation, persistence,
  RTL, catalog parity and provider behavior;
- `__tests__/i18n-fallback.test.ts` — English fallback with a mocked partial
  Spanish catalog;
- `__tests__/i18n-screens.test.tsx` — dashboard renders in `en` and `es`;
- `__tests__/i18n-send-form.test.tsx` — send form renders in `en` and `es`.

To run one file or one test by name:

```bash
npx jest __tests__/i18n.test.tsx --runInBand
npx jest __tests__/i18n.test.tsx -t "define exactly the same keys" --runInBand
```

Before opening the PR, also run the project's static checks:

```bash
npm run type-check   # tsc --noEmit — catches Locale/map registration mistakes
npm run lint         # eslint . --max-warnings=0
```

All of these should pass without warnings. If you changed test expectations
merely to make a failure disappear, stop: the failure usually means a catalog
key is missing, a placeholder was translated, or a registration entry was
forgotten.

## Pull request checklist

Copy this into your locale PR:

- [ ] `frontend/locales/<code>.json` created from `en.json`
- [ ] Every key translated; no empty strings, no leftover English
- [ ] All `{placeholders}` preserved exactly
- [ ] `frontend/lib/i18n.ts`: import, `Locale`, `SUPPORTED_LOCALES`,
      `LOCALE_LABELS`, `MESSAGES`, `isLocale()` updated
- [ ] `RTL_LOCALES` updated if the language is right-to-left
- [ ] Settings picker shows the native language name
- [ ] `frontend/__tests__/i18n.test.tsx` parity/expectations updated
- [ ] `npm test -- i18n` passes
- [ ] `npm run type-check` and `npm run lint` pass
- [ ] Manually checked the language after a page reload
- [ ] Native/fluent speaker has reviewed the translation (say who)
- [ ] PR body links the locale request with `Closes #…`

Questions about terminology or a plural form the current keys cannot express?
Open an issue or ask in the community channels listed in
[`CONTRIBUTING.md`](../CONTRIBUTING.md#-community--discussion) before guessing.
